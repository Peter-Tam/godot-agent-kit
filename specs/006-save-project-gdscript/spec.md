# Feature Specification: Safely Save an Open Project GDScript

**Feature Branch**: `spec/006-save-project-gdscript`

**Created**: 2026-10-02

**Status**: Draft — quality-validated and ready for planning; implementation is not authorized.

**Input**: Generated feature description supplied to `/speckit.specify`:

> Safely save the exact currently observed buffer of one existing, already-open standalone GDScript in an explicitly selected authorized local Godot project and live editor session. The caller can already discover, observe, open, edit and close scripts, but still needs the developer to persist pending buffer work independently of a new agent edit. Close Phase 1's standalone Save gap, including saving a deliberate human edit or the source restored by ordinary native Undo/Redo, without adding independent history controls.

> A Save request explicitly identifies the buffer revision to preserve and its expected disk, loaded-Script and document/session state. It is not a request to supply replacement source or to save whatever happens to be current later. Admit ordinary attributable unsaved buffer work only when fresh independent observations establish that persisting that exact work is safe; dirty state is not itself a refusal for this explicit Save. Refuse unresolved disk/Resource conflicts, newer human changes, stale or absent revision/identity evidence, ambiguous or replaced sessions, closed/missing/unsupported targets, denied or outside-project access, unsafe effects and missing safety observations. Freshly observing a conflict does not authorize resolving it. Preserve the buffer text, selection, native Undo/Redo history and every unrelated document; never use Save All, discard, reload, merging, force overwrite or a prompt to manufacture eligibility.

> Use native editor save semantics as the canonical route and independently verify that the intended buffer remains open, its exact source is persisted as D == R == B, and attributable dirty/synchronization state is clean. A save acknowledgment, disk write or saved marker alone is not success. Report an already-clean coherent target as independently verified unchanged without a new write or history action. Saving source is not a parse-validity or gameplay-correctness claim: an otherwise safely saveable syntax-error buffer remains preservable and its available diagnostics are distinct from persistence success. Distinguish acceptance, effects, persistence/synchronization and verification, preserving known partial effects and uncertainty on failure, interruption or post-application human activity. Never imply rollback, automatically retry or overwrite newer work to force success.

> Prove useful dirty-to-saved transitions, equal-text-but-dirty handling, clean no-change recognition, stale/conflict/effect refusals, unrelated-work and real native-history preservation, bounded interruptions, repeated Saves and composition with the completed discovery/open/observe/edit/close/reopen workflow. Maintain applicable A–E and ordinary Save/reparse/rescan/runtime durability guarantees using independent real-editor evidence and the repository's affected-scope/cumulative-evidence policy. Preserve authenticated local routing, project confinement, source privacy, protocol-independent ownership and production-export isolation. Completing this feature does not by itself complete Phase 1.

> Exclude independent Undo/Redo commands, autosave, Save All, Save As/new files, save-and-close, closed-document persistence, embedded or non-GDScript documents, conflict resolution or force writes, batch and concurrent-agent orchestration, generalized transaction/persistence infrastructure, MCP, scene/resource/project-setting authoring, runtime/debugger/language-intelligence tools and distribution expansion. Leave interfaces, revision representation, save mechanisms, internal design, limits and exact supported environments to planning. Introduce no new service, framework, dependency, approval layer, CI topology or operational prerequisite without a concrete current need under Principle XIII.

## User Scenarios & Testing *(mandatory)*

The primary caller is a coding-agent automation layer acting for a developer who may continue working in the live editor. This capability saves **one existing, already-open standalone project GDScript** without making a new source edit. It persists the particular buffer work the caller has observed and explicitly chosen to save, not an arbitrary replacement or a later version obtained by silently refreshing stale intent.

**D** is source on disk, **R** is source held by the loaded Godot Script, and **B** is source in the live editor buffer. They remain independent authorities. **Verified saved** means the intended B source is independently observed as `D == R == B`, the same document remains open, and its document-attributed dirty state is clean with persistence and synchronization established. It does not mean the source is parse-valid or the game is correct.

**Saveable pending work** is document-attributed unsaved buffer work with an established, non-conflicting saved-source basis. D still represents that established persisted state; R is independently established as the corresponding saved source or the intended buffer source, with any difference attributable to that document's pending edit rather than competing work. An unexplained third source, independently changed disk source, unresolved external-change conflict or missing attribution is not made safe merely by collecting a fresh snapshot. Equal text does not establish clean state: an observably dirty document whose source already equals D still needs a saved-state transition.

The caller's **expected Save basis** binds its chosen buffer source and the independently observed D/R/B, document-specific dirty/version state, and project/session/document identity. The representation and way of establishing the saved-source relationship belong to planning. The observable requirement is that Save cannot overwrite a conflicting revision, persist a newer unrequested buffer, or mark newer unsaved work clean. Approval cannot substitute for these facts.

Stories are independently verifiable outcomes of one capability. Human-work protection, effect confinement, history preservation and truthful verification are inseparable from its first exposed Save path.

### User Story 1 - Persist the Exact Pending Buffer Work (Priority: P1)

As a coding-agent caller, I want to save the observed script buffer without submitting another edit, so the developer's intended work becomes durable and the existing clean-close workflow can proceed.

**Why this priority**: Existing editing persists its own clean-start changes and correctly refuses a dirty buffer. It does not provide independent persistence of human edits or source restored through native history.

**Independent Test**: In a real editor, create a distinctive unsaved change in an existing open script. Independently establish its saved-source relationship, D/R/B, dirty state and expected Save basis. Request Save and compare the outcome with independent source, open-state and clean-state witnesses.

**Acceptance Scenarios**:

1. **Given** an exact authorized target with supported saveable pending work and a current expected Save basis, **When** Save is requested, **Then** that exact buffer source is persisted without changing B or closing the document. Verified saved is returned only after independent D/R/B agreement and attributable clean/synchronized state. No developer Save or reconciliation is needed.
2. **Given** ordinary pending work for which R still contains the established saved source, or R already contains the intended B, **When** Save is requested with current attributable evidence, **Then** the supported cases converge to the exact intended source without treating all normal dirty-state divergence as a conflict or pretending R was already synchronized. No independently competing R may be overwritten.
3. **Given** the target is observably dirty even though its source equals D, **When** a current explicit Save is requested, **Then** the operation establishes and verifies the actual clean saved state while preserving source and native history. It is reported as a saved-state transition, not an already-clean no-op inferred from text equality.
4. **Given** the target is already clean, D/R/B independently agree and its expected basis is current, **When** Save is requested, **Then** the result reports verified unchanged without a source write, save action, dirty-state change or history entry. Missing safety evidence or a stale basis cannot receive this result merely because sampled text matches.
5. **Given** otherwise safely saveable supported buffer work contains a syntax error, **When** Save is requested, **Then** the exact source can be persisted with the same independent coherence/clean-state requirements. Available source-attributed diagnostics remain explicit; persistence success does not claim a valid parse or repair the source. An unsafe execution/effect context remains a separate refusal.

### User Story 2 - Refuse Conflicting or Stale Save Intent (Priority: P1)

As a developer, I want Save to preserve the work I actually chose and refuse conflicting or newer state, so an agent cannot use persistence to bypass dirty-buffer or stale-write protection.

**Why this priority**: Save intentionally changes disk and possibly loaded source. Knowing the current buffer text alone is insufficient to authorize replacing another source authority or marking new human work saved.

**Independent Test**: Prepare independently witnessed disk/Resource conflicts, stale bases, missing observations and document replacements. Inject human edits and target changes between initial observation and the effect boundary; compare source, dirty state, selection and history before and after each refusal.

**Acceptance Scenarios**:

1. **Given** D changed independently from the document's established saved state, R contains conflicting work, or the origin of a source disagreement cannot be established, **When** Save is requested, **Then** it refuses with the actual conflict or unavailable-safety reason and changes no source or saved state. Supplying a newly observed revision of the conflict does not authorize overwriting it.
2. **Given** the caller omits a usable expected basis, or any relevant source, dirty/version or identity evidence no longer matches it, **When** Save is attempted, **Then** it refuses before effects. It does not silently adopt current B, weaken the basis to a path/text comparison, or fall back to unconditional persistence.
3. **Given** the human types, performs Undo/Redo, saves, or closes/reopens the same path after observation, including a change that returns to identical text, **When** the attempt reaches its effect boundary, **Then** changed version, dirty or document identity prevents stale application. A new buffer is not the old target, even in the same session.
4. **Given** open state, required D/R/B, document-attributed dirty state or the saved-source relationship cannot be safely established, **When** Save is requested, **Then** it refuses with explicit unavailable facts rather than assuming cleanliness, copying one authority into another as evidence, or loading/reloading state to manufacture eligibility.
5. **Given** ambiguous selection, an ended/replaced or unavailable session, denied/outside-project access, a closed or missing target, an embedded/non-GDScript document, or unsupported source representation, **When** Save is requested, **Then** an actionable distinct refusal occurs before effects, with no guessed target or unauthorized/candidate source. A surviving buffer with a missing file is preserved, not recreated on disk.
6. **Given** the file or parent path is replaced or redirected, or the document/session identity changes before persistence, **When** the operation proceeds, **Then** it cannot write or mark saved the replacement under the older authorization. Detected invalidation prevents effects; inability to protect that boundary requires refusal.
7. **Given** another kit operation overlaps a Save, **When** the requests approach their effect boundaries, **Then** existing single-editor operation protection prevents competing application. A refused request cannot run later, is not queued or automatically retried, and does not interfere with human typing.

### User Story 3 - Keep Save Local to One Document and Preserve Native History (Priority: P1)

As a developer, I want an agent's Save to behave like saving my chosen document, not like applying all pending scripts or replacing editing history.

**Why this priority**: Persisting the right target is still unsafe if Save applies another tab's work, executes unpermitted code or destroys real Undo/Redo.

**Independent Test**: Save selected and non-selected targets while other documents contain distinctive unsaved work and usable history. Exercise actual native Undo and Redo across Saves, including saving the undone and redone states, and independently observe each authority and dirty state.

**Acceptance Scenarios**:

1. **Given** an eligible target and unrelated dirty documents, including pending B differing from their R, **When** the target is saved, **Then** those documents retain source, dirty state, open state, selection and usable history. A supported target-only path succeeds with unrelated human work present; a context whose native effects cannot preserve that work refuses before effects instead of applying or saving other buffers.
2. **Given** an eligible target in a non-selected tab, **When** Save is requested, **Then** it acts on that exact document without selecting it or another tab, and leaves the same document open. Editor focus does not choose the target or supply missing observability.
3. **Given** a target with earlier native undo history and a pending edit, **When** it is saved, undone, saved at the restored source, redone and saved again, **Then** the actual history restores/reapplies the expected complete sources in native order. Each Save independently establishes persisted D/R/B agreement without adding a synthetic source-history action, clearing earlier entries or disposing of the redo branch. Ordinary unsaved state after Undo/Redo is reported as such until separately saved.
4. **Given** a refused or verified-unchanged Save, **When** native history is subsequently exercised, **Then** it behaves as before the request with no added, removed or reordered entries. Save does not claim that a disk write itself is an undoable edit.
5. **Given** the Save context would execute project code, access unauthorized dependencies, apply unrelated pending source, require a destructive prompt or cause other unpermitted effects, or the required effect safety cannot be established, **When** Save is attempted, **Then** it refuses before those effects. Ordinary native save bookkeeping and source revalidation are permitted only when confined by the same preservation and verification rules; this is not permission for arbitrary execution or a general reparse command.

### User Story 4 - Understand Interrupted and Partly Completed Saves (Priority: P1)

As a coding-agent caller, I want a failed Save to tell me what changed and what is unknown, so I do not assume rollback, retry stale intent or overwrite newer human work.

**Why this priority**: Source synchronization, disk persistence and clean-state bookkeeping may fail at different points. Neither an acknowledgment nor a clean marker proves that all postconditions passed.

**Independent Test**: Exercise controlled failures before effects, during synchronization/persistence, after a disk change and during verification. Include disconnection, cancellation, an unresponsive editor and human changes after application; compare results against independent surviving-state witnesses.

**Acceptance Scenarios**:

1. **Given** Save is acknowledged or a disk/loaded-source/saved-state effect occurs before independent verification completes, **When** a result is returned, **Then** it does not claim verified saved. It distinguishes accepted, applied, persisted/synchronized and verified stages with known effects, unavailable evidence and their validity.
2. **Given** source cannot be written, persistence fails, or disk, loaded source, buffer or clean-state verification fails, **When** the attempt terminates, **Then** the result reports the specific failure and independently known changes. A failure detected before effects causes no changes; a failure after possible effects is not relabeled as definitely not applied or silently rolled back.
3. **Given** cancellation, timeout or disconnection occurs, **When** the attempt terminates, **Then** it distinguishes proven no effects from known/partial effects and effects unknown. A proven no-effect result cannot later write, synchronize or mark a document saved. Every controlled local request, including an unresponsive editor, returns within ten seconds.
4. **Given** the human changes or reopens the document after application begins but before verification finishes, **When** verification occurs, **Then** the newer text, dirty state and history remain intact. The operation does not mark newer work clean, reassert the older source, close/reopen the document, or return success from invalidated earlier observations.
5. **Given** an interrupted attempt may have applied, **When** the caller considers another operation, **Then** the result directs it to freshly observe the same explicit target and establish a new valid basis. No automatic retry, compensating edit, replay against a replacement session or unconditional idempotency claim is made.

### User Story 5 - Complete and Repeat the Persisted Script Workflow (Priority: P1)

As a developer, I want independent Save to compose with the completed script workflow and remain reliable across repeated work, without changing the meaning of existing operations.

**Why this priority**: A one-off save is insufficient if subsequent Save, history, closing, reopening or editing loses the persisted source or weakens existing refusal behavior.

**Independent Test**: Discover/open/observe an eligible script, introduce deliberate human or native-history buffer work, explicitly save it, obtain fresh state, close and reopen through the existing capabilities, and continue with a guarded edit. Repeat Saves and unsafe requests with independent real-editor witnesses and applicable durability checks.

**Acceptance Scenarios**:

1. **Given** an eligible script selected through existing discovery and opening, **When** the caller explicitly saves observed pending work, freshly observes, closes and reopens it, **Then** the saved source remains intact and reopened D/R/B agree without manual Save, tab management or reconciliation. A later existing edit requires its own fresh basis and retains its unchanged clean-start rules.
2. **Given** at least 20 Save requests with deliberate intervening human edits and history transitions, **When** the sequence includes at least five actual dirty-to-saved transitions, five freshly based clean no-change recognitions and five stale/conflicting/unsafe refusals, **Then** no intended saved revision disappears before an intentional change, no newer or unrelated work is lost, and every result reflects its actual document identity and independently observed state.
3. **Given** saved source and the composed existing edit/history workflow, **When** applicable A–E, ordinary subsequent Save, close/reopen, reparse, rescan and permitted fixture-runtime durability checks are exercised, **Then** successful revisions remain durable, native history stays usable while its buffer exists and no agent-created divergence requires reconciliation. Syntax-error persistence does not falsely claim successful runtime execution; a valid-source fixture establishes applicable runtime durability.
4. **Given** the capability is installed and authorized, ambiguous, denied and interrupted requests are exercised with distinguishable source sentinels, **When** existing operation results, incidental logs, routing metadata and production exports are inspected, **Then** existing discovery/observation/open/edit/close meanings, limits and deadlines remain unchanged, no unauthorized or incidental source is exposed, and Save tooling neither ships as active gameplay behavior nor becomes a gameplay dependency.

### Edge Cases

- Empty source is a real buffer value. Whitespace or line-ending differences must not be normalized into false agreement; unsupported representation/size limits require explicit refusal, never silent truncation or rewriting.
- A dirty buffer textually equals disk, or a human edits away and back to the same text. Saved-state and revision/identity evidence, not source equality alone, determine eligibility and whether a saved-state transition occurred.
- A loaded Script already matches the dirty buffer versus still holding its established saved source. Both ordinary attributable pending states need useful support; unexplained divergence or conflicting Resource work must not be normalized away.
- Disk was changed independently before the caller's latest observation. A fresh snapshot must not turn an unresolved external-change conflict into authorization to overwrite it.
- A missing, renamed or replaced file still has an open buffer. Save preserves that work and refuses this existing-file operation; it does not create a new path, implement Save As or retarget a replacement.
- Write permission disappears or persistence fails after R has changed. Report the actual stage and partial state; do not claim not-applied, mark unsaved data clean or restore old source over newer work.
- A Save triggers editor bookkeeping or source revalidation. All attributable effects and required continuations remain inside the attempt's safety/verification boundary; unexpected effects cannot be hidden behind a successful disk write.
- A syntax-invalid script is safely persisted. Saving text and proving that it runs are different outcomes; available diagnostics and unsupported effect contexts remain explicit.
- The document is closed/reopened or the session restarts with identical source. The replacement has a new identity; an old request cannot save or mark it clean.
- An initially clean file is read-only. Verified no-change recognition needs no write merely to prove it is already saved; a dirty target that requires unavailable write access must refuse or report a truthful persistence failure without bypassing permissions.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The caller MUST be able to explicitly save the exact observed buffer of one existing, already-open standalone project GDScript in one authorized local editor-session lifetime. The intent MUST identify the chosen buffer revision and expected Save basis, not provide a new source edit or authorize saving whatever version appears later. Closed-document persistence, file creation and implicit Save inside existing operations are excluded.
- **FR-002**: Selection and effects MUST preserve existing authenticated, local, project-confined and lifetime-bound routing. Ambiguous, ended/replaced, unauthorized or escaping targets MUST NOT select by focus, expose candidate source, start an editor or substitute another session/document. Missing, invalid, closed, unknown-open and unsupported targets MUST remain distinguishable.
- **FR-003**: Before effects, the system MUST independently establish current D/R/B, open-document identity, document-attributed dirty/version state and the non-conflicting saved-source relationship. Saveable pending work as defined above MUST be supported, including ordinary R-at-saved-source and R-at-buffer-source cases and equal-text-but-dirty state. Unresolved disk/Resource conflicts, unexplained divergence, known stale state outside that attributable pending transition and missing/invalidated required evidence MUST refuse. Fresh observation or caller approval MUST NOT resolve a conflict by itself.
- **FR-004**: A usable expected Save basis MUST protect the chosen buffer source and relevant disk, Resource, dirty/version, document and session state. Omitted, stale or unusable evidence MUST refuse; same-text changes MUST NOT bypass version or identity protection. Checks MUST remain valid at each applicable effect boundary, including persistence and marking clean. Path/parent replacement MUST NOT redirect writes; replacement buffers/sessions MUST NOT inherit old authority. Existing single-editor kit-operation protection MUST prevent competing and late refused effects without freezing human typing.
- **FR-005**: Save MUST use Godot-native save/transaction semantics as the canonical route wherever possible, preserving equivalent guarantees for any justified alternative. It MAY synchronize the admitted target's R to the exact intended B, persist that source to its existing D and establish its saved state. It MUST NOT change B, discard work, reload conflicting source, merge, force overwrite, close/open/select documents, Save All, apply unrelated pending buffers, execute project code, accept a destructive prompt or access unauthorized dependencies. Required native bookkeeping/revalidation MUST be effect-confined and independently verified; unsafe or unobservable effect contexts MUST refuse before dispatch.
- **FR-006**: Source, dirty/open state and usable native history of unrelated documents MUST remain unchanged by Save. The target MUST retain its buffer text, identity, selection and native Undo/Redo ordering, including its redo branch; Save MUST add no synthetic source-history action or erase earlier entries. Actual native Undo and Redo across intervening Saves MUST restore/reapply the corresponding complete sources, and each explicitly saved state MUST independently converge on D/R/B. Saving does not itself introduce an undoable source edit or persistent history after ordinary close.
- **FR-007**: Verified saved MUST require fresh independent evidence that the exact intended source is persisted as D == R == B, the same document remains open, document-attributed dirty state is clean, and disk/Resource/editor synchronization is complete without detected invalidation. A write return, saved marker, acknowledgment, copied input or remaining equal pair MUST NOT substitute for independent evidence. Missing, conflicting or invalidated postconditions MUST prevent success.
- **FR-008**: A currently clean target with independent D/R/B agreement, matching basis and all required current checks MUST receive verified unchanged without source writes, a save action, dirty-state change or history mutation. Equal-text-but-dirty state MUST instead receive a verified saved-state transition if successful. Neither result may imply a new source edit or prove that an earlier interrupted request succeeded.
- **FR-009**: Save success MUST describe persistence/coherence, not parse validity, diagnostic freedom or gameplay correctness. Syntax errors alone MUST NOT prevent preserving otherwise supported safe buffer work. Available diagnostics MUST retain source/revision attribution and explicit availability; unavailable optional parse diagnostics MUST NOT be invented as clean results. Unavailable evidence required for effect safety or coherence still MUST prevent application/success as appropriate. The existing edit capability's valid-post-change-parse requirement remains unchanged.
- **FR-010**: Every attempt MUST distinguish acceptance, effect initiation/application, persistence/synchronization and independent verification. Results MUST expose the requested/resolved target or refusal reason, expected and observed revisions/identities, intended buffer attribution, reached stage, known disk/Resource/saved-state effects, D/R/B availability and synchronization, dirty state, relevant diagnostics, native-history preservation/participation, evidence interval/validity and partial failures. Unknown facts MUST carry explicit limitations rather than inferred values.
- **FR-011**: Structured outcomes MUST distinguish verified saved, verified unchanged, refused with no effects, applied/partly applied but unverified, and effects unknown. Reasons MUST distinguish stale basis/identity, unresolved disk or dirty/Resource conflict, other divergence, known stale Resource/buffer, missing safety evidence, ambiguous/missing/invalid/closed/unsupported target, unsafe effects, permission/access denial, unavailable/disconnected editor, persistence/synchronization failure, timeout and cancellation wherever applicable. A dirty target intended for Save MUST NOT be indiscriminately classified as an edit-style dirty refusal; parse diagnostics MUST remain distinct from persistence failure.
- **FR-012**: Every controlled local Save request MUST return a terminal result within ten seconds, including an unresponsive editor or blocked persistence case. Timeout, cancellation and disconnection MUST NOT imply rollback or definitely-not-applied state. A no-effect result requires evidence that no effects occurred and none can occur later from that attempt; otherwise known effects or uncertainty MUST remain explicit. Existing operation deadlines remain unchanged.
- **FR-013**: Pre-effect refusals MUST cause no source, saved-state, selection, lifecycle or history change. During application and verification the system MUST preserve newer human work and MUST NOT mark it saved, replace it with the older intended source, restore older disk/Resource values as implicit rollback, close/reopen the document or force postconditions after invalidation. Known changes and safely attributable partial evidence MUST survive in the non-success result.
- **FR-014**: Save attempts MUST NOT automatically retry, queue a refused action for later execution or replay against replacement state. After possible application, the safe next action MUST require fresh explicit-target observation and a new valid basis before another mutation. A later fresh request may recognize already-clean state under FR-008; this MUST NOT be advertised as unconditional replay safety.
- **FR-015**: Source limits and availability/attribution meanings MUST preserve existing observation behavior. Unsupported representation or size and missing required safety evidence MUST refuse before effects where detectable; unexpected post-application evidence loss MUST produce an unverified outcome with known effects. Source MUST NOT be truncated, copied between authorities as evidence, normalized into agreement or represented as empty when unavailable.
- **FR-016**: Completed discovery, observation, opening, editing and closing MUST retain their existing contracts, limits, deadlines and safety behavior. Observation/discovery remain non-interfering; existing edit and close still refuse dirty state rather than implicitly saving it. A caller MUST be able to compose explicit Save with fresh observation, eligible close/reopen and subsequent guarded editing. No earlier operation or Save result grants reusable mutation permission.
- **FR-017**: The feature MUST preserve protocol-independent common transaction semantics and the architectural separation of caller interaction, automation core and Godot integration. It MUST NOT introduce a parallel mutation policy, MCP exposure, alternate history or gameplay authority.
- **FR-018**: Save MUST preserve local-only operation, authentication, project confinement, no telemetry, source-free private routing metadata and existing permission boundaries. Only explicitly requested authorized results may contain selected source; incidental logs/metadata MUST NOT expose project contents, unauthorized paths or credentials. No arbitrary-filesystem, remote/network, execution, force or approval-bypass capability is introduced. Development/export isolation MUST remain explicit and verified.
- **FR-019**: Real-editor acceptance MUST establish positive dirty-to-saved behavior, clean recognition, conflict/stale/effect refusals, protected identity/version transitions, preservation of unrelated work and actual native history, truthful interruptions, repeated use and the composed workflow. Applicable A–E and Save/close-reopen/reparse/rescan/runtime durability guarantees MUST remain satisfied. Pure decision logic and changed boundaries/transitions MUST receive proportionate deterministic isolated coverage. Refusing all dirty work, supporting only clean no-ops, or relying on disk/headless/mocked evidence alone does not satisfy the feature.
- **FR-020**: Exact supported Godot versions/environments and verified limitations MUST be documented from applicable CI and real-editor evidence before support or completion is claimed. Cumulative acceptance MUST cover the requirements with valid evidence under the repository testing policy; prior feature evidence is not proof of the new Save behavior. Inapplicable surfaces/scenarios require substantive recorded justification; missing required observability is not a passing result.

### Outcome Interpretation

These meanings describe caller-visible behavior, not a prescribed interface, wire schema or new transaction framework.

- **Verified saved**: The request performed an admitted persistence or saved-state transition and independent postconditions passed for the intended buffer. Equal-text-but-dirty may qualify without a source-text change; the outcome reports the actual effects rather than inventing a new edit.
- **Verified unchanged**: The exact currently observed target was already clean and coherent, the expected basis and current checks passed, and the request caused no save or source/history change.
- **Refused, not applied**: Evidence establishes no request-caused effect and that this attempt cannot cause effects later. The reason and permissible observations remain explicit.
- **Applied or partly applied, unverified**: At least one disk, Resource or saved-state effect is established but required persistence/coherence/preservation or verification did not pass. Calling the attempt unsuccessful does not erase its changes.
- **Effects unknown**: Evidence cannot establish whether or how far Save applied. A missing response is not evidence of no disk write, no Resource change or rollback.

Results describe their observed interval, not a freeze on future human work. An observed dirty state is expected input to explicit Save only when it is the attributable work selected by the caller and all safety facts hold. Unknown dirty state is not clean; ordinary pending divergence is not permission to reconcile a separate conflict. A new save intent preserves existing buffer work, whereas an edit intent replaces source; the two operations retain distinct eligibility without weakening the common safety guarantees.

Saving pending human work or a native Undo/Redo result is deliberate preservation, not a general conflict-resolution workflow. Existing edit/close refusal is not relaxed.

Out of scope are independent Undo/Redo commands, autosave, Save All/batches, Save As/new files, save-and-close, closed-document saving, embedded/non-GDScript documents, renaming/deleting files, conflict merging/discard/force writes, concurrent-agent orchestration, generalized core/persistence infrastructure, MCP, scene/resource/project-setting authoring, runtime/debugger/language-intelligence tools and distribution/platform expansion. Native history and permitted fixture-runtime actions are acceptance interactions, not additional product controls. Independent history controls and the Phase 1 exit assessment remain pending after this slice.

The [constitution](../../.specify/memory/constitution.md), [working agreement](../../AGENTS.md), [Phase 1 roadmap](../../ROADMAP.md#phase-1--live-editor-script-coherence), [architecture](../../ARCHITECTURE.md) and [testing policy](../../TEST_POLICY.md) govern this work. Principles I–IV require independently observed D/R/B, preservation of human work, native transaction semantics and verified postconditions. V and X require confinement and truthful failures. VI and XII require real-editor correctness evidence, while VII–XI preserve protocol independence, tooling isolation, a small surface, privacy and independent implementation. Mutation-semantic and security-sensitive planning/review must explicitly record constitutional compliance.

**Principle XIII boundary:** The present gap is inability to persist existing pending buffer work through the kit without asking a human to Save. The simplest alternative, resubmitting it through editing, is insufficient: editing deliberately refuses dirty state and represents a new source change, not persistence of that work. A clean-only Save would not close the gap, and an unguarded native Save may apply unrelated work or overwrite competing disk state. The smallest useful scope is one explicit guarded Save reusing current routing, observations and common transaction protection. Its necessary cost is saved-source eligibility, confined persistence/saved-state verification and native-history/real-editor transition evidence, justified by removing that manual step without losing work. No autosave service, general persistence framework, alternate history, new dependency, approval layer, CI topology or operational prerequisite is selected. Planning must justify any additional mechanism against a concrete present risk, simpler alternatives, existing limitations and ongoing cost.

Save creates no new source-history entry, but preservation of real Undo/Redo across Saves is explicitly claimed and must be observed. Applicable A–E remain required in the composed workflow: clean agent edit, refusal of unsafe human/stale conflicts, actual history transitions, caller-driven Save and close/reopen persistence, and sequential work without lost revisions. Ordinary Save/reparse/rescan and permitted runtime durability must remain satisfied where applicable. A safely saved syntax-error fixture cannot establish runnable behavior; valid-source fixtures provide that applicable proof. Independent witnesses must inspect actual live authorities and history, not infer them from disk or acknowledgment.

Verification scope follows [TEST_POLICY.md](../../TEST_POLICY.md): prove new Save transitions and composed interactions, rerun evidence invalidated by changed behavior, and reuse unaffected evidence only after relevant-input review. This specification requires complete valid coverage, not automatic reexecution of every historical campaign at each task head. It creates no new runner/provider or approval requirement and does not declare a release candidate or Phase 1 completion.

### Key Entities *(include if feature involves data)*

- **Save target**: One authorized local project, editor-session lifetime and existing open standalone script/document identity; a path alone does not identify a reopened buffer.
- **Save intent and expected basis**: The specific already-observed buffer revision chosen for persistence, with independently attributed disk/Resource/buffer, dirty/version and identity expectations. It neither supplies replacement source nor resolves an existing conflict.
- **Saved-source relationship**: Evidence distinguishing ordinary pending work from a separately changed disk/Resource or untraceable disagreement. Unknown relationship is a safety limitation, not permission to choose an authority.
- **Save evidence**: Before/after source and dirty observations, identity/revision validity, persistence/synchronization, attributable effects, relevant diagnostics, history preservation and unavailable facts.
- **Save outcome**: Reached stage, saved versus already-clean state, known/partial/unknown effects, independently verified postconditions or distinct refusal/interruption reasons, and safe next action.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every supported pending-work acceptance case, including R at saved source, R at intended buffer source, equal-text-but-dirty, non-selected and safely saveable syntax-error targets, preserves the exact chosen B and ends with independently verified D/R/B agreement and attributable clean state before success. The developer performs no manual Save or reconciliation. Every eligible already-clean case causes zero save/source/history changes.
- **SC-002**: Every conflict, stale/missing-basis, same-text version change, identity replacement, missing-observation, denied/escaping and unsafe-effect case refuses without operation-caused source, saved-state, selection or history changes before effects. An independently changed disk or Resource is never overwritten merely because it was freshly observed; no proven refusal applies later.
- **SC-003**: Every history case demonstrates actual native Undo → Save → Redo → Save with the corresponding complete persisted sources, usable earlier history and preserved redo eligibility. All Saves, refusals and unchanged requests add zero synthetic source-history entries; all unrelated-work cases preserve source, dirty state and usable history.
- **SC-004**: Every interruption, persistence failure and post-application human-change case reports stages, effects and uncertainty consistent with independent witnesses, with zero false verified-success, definite-no-effect, clean-newer-work or rollback claims. Every controlled request, including blocked/unresponsive cases, terminates within ten seconds.
- **SC-005**: At least 20 real-editor Save requests include five dirty-to-saved transitions, five freshly based clean no-change results and five stale/conflicting/unsafe refusals, with intervening human edits and native history. No intended saved revision disappears before intentional replacement, no newer or unrelated work is lost, and the final saved source survives supported close/reopen.
- **SC-006**: A caller completes discovery/open/observation, explicit Save of pending work, fresh observation, close/reopen and a subsequent guarded edit without manual path lookup, tab management, Save or reconciliation. Applicable existing A–E, native history and Save/reparse/rescan/runtime durability retain valid evidence coverage; existing operations retain their specified outcomes, limits and deadlines.
- **SC-007**: For every acceptance case, a reviewer using the result alone can identify the target or refusal, the intended buffer revision, reached stage, known/partial/unknown effects, actual D/R/B and dirty-state evidence, diagnostics/history limitations and safe next action. Privacy/export checks establish zero unauthorized or incidental source disclosure and no active shipped Save tooling or gameplay dependency.

## Assumptions

- Features 001–005 are complete according to current authoritative task/acceptance records and [project status](../../PROJECT_STATUS.md). Their implementations are reused, not reopened. Normal prerequisite-delivery sequencing still governs later implementation; this specification starts no task.
- The caller can identify one local project/editor and an existing open script, and can obtain the state needed to express a current Save basis. This does not presume that today's edit-only basis representation is sufficient for every dirty-state case; representation and safe acquisition remain planning work.
- An explicit Save is authorization to preserve the particular observed pending buffer, not permission to overwrite conflicting disk/Resource state, persist later unseen work or bypass missing safety evidence. No added per-request approval ceremony is required by this specification.
- Positive pending-work behavior is essential. Supporting only clean recognition or refusing every dirty script does not fulfill the feature. Exact supported contexts and limits require evidence without omitting the specified ordinary pending states.
- Persistence success is independent of parse validity. Safety may still require effect-related evidence; a parse error and an unsupported execution context must not be conflated. Valid-source runtime evidence and safely preserved invalid-source evidence establish different claims.
- Save preserves native source history but is not itself a new undoable text edit. Ordinary human Undo/Redo remains an acceptance interaction; standalone history controls and history retention across ordinary buffer disposal are not introduced.
- Ten seconds bounds one controlled local Save result, consistent with existing mutation/lifecycle deadlines, not arbitrary project size or concurrent throughput. Planning defines reproducible fixtures and supported limits.
- Human activity and external changes remain possible. Known/detected interference must invalidate affected safety/success claims. As in the completed editing contract, this does not promise atomic exclusion against an arbitrary non-cooperating external writer during the physical commit interval or add cross-editor leases/distributed coordination.
- APIs, expected-basis representation, persistence/saved-state mechanisms, internal boundaries, transport evolution, dependencies, exact support environments and evidence collection remain planning decisions under current architecture and Principle XIII. No engine modification, stack change or expanded compatibility claim is selected here.
- This specification and its quality checklist establish requirements only. Approval, clarification if needed, planning, task derivation, granularity review, analysis, implementation and acceptance remain separate stages. Specification creation does not complete this feature or Phase 1.
